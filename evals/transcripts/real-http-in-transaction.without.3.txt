Ревью ПринятьЗаказ

Есть критичный дефект.

1. Критично: HTTP-вызов внутри транзакции (строки 9-10). Соединение.Получить(...) выполняется между НачатьТранзакцию и ЗафиксироватьТранзакцию, после Заказ.Записать(). Все время сетевого запроса (с учетом таймаутов, а их не задано) транзакция остается открытой, а блокировки на записанные данные заказа удерживаются. Это приводит к долгим блокировкам, ожиданиям и таймаутам у других сеансов, а при зависании внешнего сервиса к залипшей транзакции. Кроме того, откат транзакции не откатывает внешнее действие, то есть согласованность не гарантируется.
   Как исправить: выполнить HTTP-запрос до НачатьТранзакцию (если результат нужен для записи) или после ЗафиксироватьТранзакцию (если это уведомление/проверка статуса). Внутри транзакции оставить только Заказ.Записать().

2. Ответ не используется и статус не проверяется: нет проверки Ответ.КодСостояния, обработки ошибки сервиса. Если проверка статуса нужна для бизнес-логики, обработайте результат.

3. Не задан таймаут: Новый HTTPСоединение("api.shop.example", , , , , Таймаут) - иначе зависший сервис блокирует поток.

4. Соединение по HTTP без защищенного соединения; для внешнего API используйте Новый ЗащищенноеСоединениеOpenSSL и HTTPS.

5. Номер заказа конкатенируется в URL без кодирования; примените КодироватьСтроку(..., СпособКодированияСтроки.КодировкаURL).

Вывод: не сдавать, пока HTTP-вызов не вынесен за границы транзакции.
