Ревью ОбработкаПроведения

Вердикт: в таком виде сдавать нельзя. Есть один серьёзный дефект (внешний HTTP-вызов внутри транзакции проведения) и несколько существенных замечаний по контролю остатков.

Критично

1. HTTP-запрос к магазину внутри транзакции проведения (строки 39-42).
   ОбработкаПроведения выполняется в транзакции. Что из этого следует:
   - Сетевой вызов держит транзакцию и блокировки на регистре СвободныеОстатки на всё время ответа. При зависании магазина встанут все остальные проведения по этим складам и номенклатуре.
   - Внешний эффект нельзя откатить. Если после этого блока что-то отменит проведение (другой обработчик, подписка, ошибка фиксации), заказ в магазине уже подтверждён, а документ не проведён.
   - Нет Попытки/Исключения, нет таймаута у HTTPСоединение, не проверяется Ответ.КодСостояния. Ошибка сети приведёт к падению проведения с неинформативным сообщением, а ответ 500 будет молча проигнорирован.
   - Перепроведение документа отправит подтверждение повторно, идемпотентности нет.
   - Подтверждение (изменение состояния) делается через GET (Получить). Нужен POST/PUT.
   - Номер подставляется в URL без кодирования.
   - HTTPСоединение ожидает адрес сервера (хост), а не полный URL со схемой. Если в константе лежит URL, соединение не создастся. Пустое значение константы не проверяется.
   Как исправить: из проведения только ставить задание на отправку (регистр сведений «очередь обмена» либо фоновое/регламентное задание), а сам вызов делать после успешной фиксации, с таймаутом, обработкой ошибок, повтором и проверкой кода ответа.

Существенно

2. Контроль остатков не ограничен номенклатурой документа (строки 17-28).
   Запрос выбирает все отрицательные остатки по складу. Если по складу уже есть отрицательный остаток по товару, которого нет в документе (например, из-за старых данных), проведение заблокируется, хотя документ ни при чём. Нужно добавить отбор по номенклатуре из табличной части: передать в виртуальную таблицу условие Номенклатура В (&СписокНоменклатуры) или соединиться с Товары.

3. Права и RLS при контроле остатков.
   Запрос к Остатки выполняется с правами пользователя. Если на регистр или склад действуют ограничения доступа на уровне записей (RLS), пользователь увидит неполные остатки, и контроль даст неверный результат. Проверка целостности данных должна выполняться в привилегированном режиме. Сейчас он включается только для чтения константы, и это наоборот, а нужно для запроса.

4. Конкурентное проведение.
   Явной управляемой блокировки нет. Схема «записать движения, затем проверить остаток» корректна сама по себе, но убедитесь, что запись набора действительно ставит нужную блокировку по измерениям Склад/Номенклатура. Если режим блокировки данных управляемый, надёжнее явно установить БлокировкаДанных на регистр по проверяемым измерениям перед записью. Иначе два документа, проводимые одновременно, могут оба пройти контроль на одном и том же остатке.

Замечания помельче

5. Движения.СвободныеОстатки.Записывать = Истина вместе с явным Записать() избыточны: набор будет записан дважды (второй раз платформой при завершении проведения). Достаточно одного из двух. Если явная запись нужна для контроля, оставьте Записать() и уберите Записывать = Истина (либо оставьте оба сознательно и поясните в комментарии).

6. Сообщения об ошибке.
   Сообщить(...) без привязки к документу. Лучше использовать Новый СообщениеПользователю с указанием поля (табличная часть Товары, строка, колонка Номенклатура) и показывать, сколько именно не хватает (Остаток и требуемое количество), а не только наименование. Строка "Не хватает на складе: " + Выборка.Номенклатура неявно приводит ссылку к строке, лучше Строка(...) или шаблон с подстановкой.

7. Не проверяются входные данные: пустой склад, нулевое или отрицательное количество в строках, пустая номенклатура.

8. Привилегированный режим включается и выключается без Попытки. При исключении между вызовами режим не сбрасывается явно (хотя в пределах серверного вызова это не критично). Блок лучше вынести в небольшую функцию получения настройки с использованием привилегированного режима только на время чтения и с проверкой, что константа заполнена.

9. Параметр РежимПроведения не используется. Если контроль остатков или внешний вызов должны отличаться для оперативного и неоперативного режимов, это нужно учесть. Если нет, ничего делать не надо.

Что в порядке

- Идея «сначала записать движения, затем прочитать остаток с границей МоментВремени() Включая» корректна: остаток считается уже с учётом текущего документа, при Отказ = Истина транзакция откатывается вместе с движениями.
- Гранича Новый Граница(МоментВремени(), ВидГраницы.Включая) выбрана правильно.
- Запрос параметризован, конкатенации в тексте запроса нет.

Итог по приоритету исправлений
1. Убрать HTTP из транзакции проведения (в очередь/после фиксации), добавить обработку ошибок и идемпотентность.
2. Ограничить контроль остатков номенклатурой документа.
3. Выполнять контроль остатков в привилегированном режиме (учёт RLS) и проверить блокировки.
4. Убрать двойную запись движений, улучшить сообщения, добавить проверку данных.
