# Как улучшать набор

Принцип: **ложный запрет хуже пропуска мелочи**, поэтому любое правило приходит с исключением и с тестом.

## Цикл «ложное замечание → тест»

1. Человек присылает случай через issue «Ложное замечание» (или «Пропущенный дефект»).
2. Случай превращается в фикстуру `tests/fixture-negative/<id>.bsl` и кейс в `evals/negative.json` (подробности в `1c-writing-skills`): код, `must_match` и `must_not_match`.
3. Прогон `evals/run_eval.py` без набора и с ним. Правило оправдано, если без него ответ ошибается, а с ним нет.
4. В карточку `skills/1c-review/*.md` добавляется исключение в блок «Не ставить» (или правило с четырьмя метками). Источник: стандарт ИТС, v8std.ru или документация платформы, текст стандарта не копировать.
5. `python3 -m unittest discover -s tests` зелёный, `python3 scripts/context_budget.py` в пределах бюджета.

## Правила для карточек
Четыре метки обязательны: «Когда ставить», «Не ставить» (с реальным исключением или «не хватает факта»), «Как доказать», «Тяжесть». Правило без исключения не принимается. Имена прикладных решений в правила не вшиваем.

## Что не принимается
Выдуманные ссылки на стандарты, цитаты из ИТС, номера версий без источника, правила, которые судят код вне diff, секреты в фикстурах.
