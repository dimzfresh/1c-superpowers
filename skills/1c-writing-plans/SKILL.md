# План работ (writing-plans)

Предмет — согласованный дизайн и структура выгрузки 1С. План — последовательность мелких задач для `1c-executing-plans`, не код.

## Когда открывать

- Дизайн согласован (`1c-brainstorming` или явное ТЗ от пользователя).
- «Разложи на задачи», «напиши план», перед большой доработкой в несколько файлов.
- Роутер направил по фразам «план работ», «по шагам».

Не открывать для однострочного typo без дизайна — достаточно точечной правки по запросу, если scope уже ясен.

## Шаги по порядку

1. **Карта файлов.** Какие **пути** затронуты: `Configuration.xml`, каталоги объектов, `Ext/Module.bsl`, формы, CFE, общие модули — относительно корня выгрузки в репо.
2. **Декомпозиция.** Задачи по **2–5 минут** каждая: один осмысленный deliverable, свой мини-цикл проверки.
3. **Шаблон задачи.** Для каждой задачи явно:
   - **Путь** файла(ов) XML или BSL;
   - **Проверка** (синтаксис, сценарий, `find_checks`, ручной прогон — что реально доступно);
   - **Риск обновления/CFE** (заимствование, `&Вместо`, снятие с поддержки) — ссылка на [../1c-review/extension.md](../1c-review/extension.md) при CFE.
4. **Границы diff.** Задачи не выходят за согласованный дизайн; новые объекты — отдельными задачами с путями метаданных.
5. **Куда сохранить.** По умолчанию — план в **ответ чата**. Файл `docs/superpowers/plans/YYYY-MM-DD-<topic>.md` — **только если пользователь просит артефакт в репо**.
6. **Передача.** Готовый план → `1c-executing-plans`; напомнить: код только по задачам плана.

## Стоп и запреты

- Не начинать правки BSL/XML в этом скилле — только план.
- Не писать сводку и вердикт сдачи — только `1c-review`.
- Не обещать «переживёт обновление» без второй выгрузки — класс **не хватает факта** в плане, не в коде.
- Не раздувать задачи: если шаг дольше 5 минут — разбить.

## Что отдать исполнителю

- **1c-executing-plans:** нумерованный список задач с путями, проверками и рисками CFE/обновления.
- **Человеку:** план (в чате или путь к файлу, если просили); вопросы только по пробелам «не хватает факта».
