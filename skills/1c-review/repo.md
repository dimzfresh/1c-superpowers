# Запрос на слияние

Термины: MR (GitLab) и PR (GitHub) — одно и то же. Рецепты ниже даны для MCP с инструментами `pull_request_*`. Для GitLab MCP или `glab` без записи ревью — тот же порядок: прочитать diff, сводку отдать в чат; публикация только по просьбе и только если инструмент реально умеет писать комментарий.

Область ревью — diff этого запроса, не вся конфигурация. Хост не угадывать. GitHub и Origin — разные MCP, владельца одного в другой не подставлять.

## Прочитать diff

MCP репозитория нет — ревью только того, что прислали в чат. Не писать, что diff прочитан.

Origin (read-only MCP без записи ревью): `pull_request_read`, вид `files`. Это чтение. Писать ревью туда нельзя. Сводка остаётся в чате, так и сказать.

GitHub: `pull_request_read` по номеру запроса. В область брать модули и XML метаданных из diff. Остальные файлы не разбирать.

Дальше обычный процесс: факты выгрузки (файлы или любой подключённый MCP метаданных, см. [facts.md](facts.md)), затем только совпавшие чеклисты.

## Опубликовать

Публиковать, только если об этом попросили. Сам запрос на ревью публикацией не является.

Один текст — сводка из этого набора. Замечание на каждую строку diff не оставлять. Внутренние карточки не вставлять.

В начало сводки ставится метка `<!-- 1c-review -->`. Такая метка в запросе уже есть — второй раз не публиковать, пока человек не подтвердит повтор.

GitHub, инструмент `pull_request_review_write`, метод `create`, тело — сводка:

| Вердикт | Событие |
|---|---|
| править | `REQUEST_CHANGES` |
| сдать с оговоркой | `COMMENT` |
| можно сдавать | `APPROVE` |

`APPROVE` не ставить, если в резюме есть «отдать человеку» или «не хватает факта».

Origin и любой MCP без записи ревью: сводку отдать в чат и написать, что этот хост публикацию не принимает. Не имитировать отправленное ревью.
