# Приём замечаний с ревью

Предмет — список замечаний ревьюера и текущий diff. Четыре класса по каждому пункту: **править**, **оспорить с доказательством**, **не хватает факта**, **отдать человеку**. Юрисдикция diff: не доказывать поведение вне присланных файлов.

## Когда открывать

- Пришли комментарии к MR, список «исправь по review», ответ на REQUEST_CHANGES.
- Роутер направил по фразам «замечания с ревью», «правки по review».

Не подменяет первичное ревью diff — для нового diff без списка замечаний открыть `1c-review`.

## Шаги по порядку

1. **Список.** Выписать каждое замечание одной строкой: модуль, процедура, суть риска.
2. **Решение на пункт.** Только одно из: **править** (согласен, правка в diff), **оспорить** (исключение из карточки или факт из diff опровергает вывод — процитировать строку), **не хватает факта** (ревьюер или ты не видите выгрузку, вторую CFE, данные конфигурации), **отдать человеку** (шаблон ограничения, порядок расширений — см. [../1c-review/handoff.md](../1c-review/handoff.md)).
3. **Правки.** Менять только то, что закрывает согласованные пункты; не «улучшать» соседний код вне замечаний.
4. **Повторная сдача.** После правок — `1c-verification`, затем `1c-review` для сводки и вердикта. Без verify не писать «исправлено, можно мержить».

## Стоп и запреты

- Не принимать замечание молча без метки: править / оспорить / не хватает факта / отдать человеку.
- Не оспаривать без цитаты из diff или явного исключения из карточки [../1c-review/](../1c-review/).
- Не писать сводку и вердикт сдачи — только `1c-review`.
- Не force push и не переписывать историю ветки без явной просьбы автора.

## Что отдать review и человеку

- **1c-review:** таблица «замечание → решение → доказательство или пробел факта», diff после правок.
- **Человеку:** что приложить, если оспорить нельзя без второй выгрузки или решения по handoff.
